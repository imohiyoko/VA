# 診断手法 概要

**設計方針: 判断が必要な小さな仕事だけを LLM に渡し、それ以外はすべて `scripts/va.py` が決定的に行う。**
これにより Haiku クラスの軽量モデルでも安定して動き、CI で回せて、結果が再現・比較できる。

## パイプライン

| 段階 | 実行者 | 内容 | 単位 |
|---|---|---|---|
| plan | スクリプト | ファイル列挙、除外、blob SHA で前回と比較、静的解析ツール実行 | run |
| summarize | **LLM** | 変更・新規ファイルだけを要約して索引化（`01-index.md`） | 1ファイル |
| (選定) | スクリプト | リスク・変更・ローテーションでレビュー対象とチェックリストを決める | — |
| review | **LLM** | 1ファイル（の1チャンク）を、選ばれたチェックリストだけで確認（`02-code-review.md`） | ファイル×チャンク |
| (集約) | スクリプト | fingerprint 計算、重複排除、抑制済みの除外、前回判定の再利用 | — |
| triage | **LLM（別プロンプト・別呼び出し）** | 候補1件を、コード周辺だけを見て検証（`06-triage-and-severity.md`） | 候補1件 |
| report | スクリプト | findings / 新規・継続・解消 / changes.md / report.md / 索引と state 更新（`07-reporting.md`） | run |
| retrospective | LLM（エージェント） | 統計（`va.py stats`）から学習を抽出し、上流候補を作る | run |

各 LLM 呼び出しは独立したプロセス（`claude -p` など）で、空のディレクトリから起動する。
そのため文脈が溜まらず、対象リポジトリの `CLAUDE.md` 等も読み込まれない。
出力は JSON スキーマで検証し、不正なら1回だけ理由付きで再試行、それでも駄目なら失敗として「未カバー」に記録する。

## コストを抑える仕組み（キャッシュ）

- **要約**: blob SHA が同じファイルは前回の要約を再利用（LLM 呼び出しゼロ）
- **レビュー**: diff モードでは変更ファイル＋高リスクの未変更ファイルを毎回 N 件ずつローテーション
- **トリアージ**: 同じ fingerprint（＝同じコード行）は前回の判定を再利用
- **フルスキャン**: `full_every` 回に1回、または VA の MINOR 以上が上がったとき

## 小さいモデルのための工夫

- 1回の入力は「1ファイル（最大 `chunk_lines` 行）＋そのファイルに該当するチェックリストだけ」
- 出力カテゴリをチェックリストごとに限定し、範囲外の行番号・カテゴリはスクリプトが捨てる
- 行番号付きでコードを渡し、行番号での指摘を必須にする
- 「見つからない」ことを正解として明示する（無理に件数を出させない）
- 判定と候補出しを別呼び出しにする（自分の出力を自分で採点させない）
- モデル固有の補正は `model-profiles/<model>.md` の `- [review] ...` のような行で注入する

## 要約を信用しすぎないための安全策

要約は対象コード（信頼できない入力）から作るので、細工で「安全」と書かせられる可能性がある。
そのため要約は**優先順位付けにだけ**使い、次は要約に関係なく強制的にレビュー対象にする。
- パス名が入口らしいファイル（route, controller, handler, api, auth, upload など）
- `kind` が entry / ci / iac
- AI 向けの指示を含むと判定されたファイル（`injection_suspect`、最優先）

## ツール

`semgrep` / `gitleaks` / `osv-scanner` が入っていれば plan で実行し、結果を候補に加える。
依存の脆弱性（osv）は LLM で到達性を判断させず、`needs_info`（reachability: unknown）として決定的に扱う。
ツールが無い・失敗した場合は report の「Not covered」に記録される。
