# 参考 6: トリアージと重大度

トリアージは**候補を出したレビューとは別の呼び出し**（`prompts/tasks/triage-candidate.md`）で、候補1件ずつ行う。
自分の候補を自分で採点しないため。

## 各候補について確認すること

1. **再現経路**: source から sink まで実際にコードを読んで辿れるか。辿れなければ `needs_info` か `false_positive`
2. **攻撃者の前提**: 未認証 / 認証済み一般ユーザー / 管理者 / ローカル / CI へのコミット権 のどれが必要か
3. **既存の緩和策**: フレームワークの自動エスケープ、ミドルウェア、WAF 前提 等
4. **影響**: 機密性・完全性・可用性のどれが、どの範囲で損なわれるか

## 判定（status）

`confirmed` / `likely` / `needs_info` / `false_positive`
（運用側で後から人が付ける: `accepted_risk`, `fixed`, `wont_fix`）

## 重大度

| 重大度 | 目安 |
|---|---|
| critical | 未認証でリモートからコード実行・全データ取得・認証回避ができる |
| high | 認証済み一般ユーザーから他人のデータ・権限に到達、有効なシークレットの露出 |
| medium | 条件付きの悪用（ユーザー操作が必要、限定的な情報漏洩、到達性不明の既知 CVE） |
| low | 防御の多層化の欠如、ハードニング不足、悪用が非常に困難 |
| info | 記録のみ（ロックファイル無し等） |

迷ったら**低いほう**を付け、理由を書く。過大評価はレポートの信頼を落とす。

## 誤検知の扱い

`false_positive` にした理由は必ず1行で書く。この理由は retrospective が
「どのチェックが誤検知を出しやすいか」「どのモデルが誤検知を出しやすいか」の学習に使う。
