# 観点: 権限昇格（付与の確かめと、権限の分類の一覧の漏れ）

「ロールを管理できる」程度の限られた権限を持つ主体が、自分の持たない権限を入れたロールを作り、自分（や他人）に付与できる。
これは 1 ファイルずつのレビューでは見落としやすい。付与の確かめそのものは正しく書かれていても、
確かめが頼る**権限の分類の一覧**（「特権の権限」「システム自身の管理用の権限」「予約済み」「テナントの範囲で使えない」など）から、
後から定義した権限が漏れていると、漏れた権限は「特権でない」扱いになって付与できてしまう。

一覧が「ある」ことはそのファイルを読めば分かるが、一覧が「足りない」ことは**定義の側と突き合わせないと分からない**。
そこでこの観点は、レビュー（1 ファイル）と、スクリプトによる突き合わせ（crosscheck）の 2 つで見る。

## 1. 付与の確かめ（レビュー、チェックリスト `privilege-escalation`）

`tags: [auth]` のファイルと、パス名がロール・権限らしいファイル（`PRIV_HINT`: role, perm, grant, rbac, acl, policy, scope など）に適用する。
後者は要約に関係なく `auth` タグを足し、risk を 2 以上にする（細工や誤りで要約から `auth` が落ちても外れないように）。

- ロール・権限・スコープ・API キーを作る/変える/付与するとき、入れる権限が呼び出し主体の権限の部分集合か
- 作成・更新・付与（既存ロールの割り当て、グループ・招待経由）のすべての経路に確かめがあるか
- ワイルドカードや包含関係を部分集合の判定で正しく扱うか、自分自身への付与も同じ確かめを通るか
- 分類の一覧が「無ければ緩い側」に倒れる作り（特権を denylist で判定）になっていないか
- 一覧が定義と別の場所に手書きされ、定義を足したときに追従する仕組み（定義側の属性、全件を調べるテスト）が無くないか
- 利用者が名前を決められるロール・権限が、内部の特権と同じ名前空間にないか。付与の範囲が付与する主体の範囲を超えないか

## 2. 定義と分類の一覧の突き合わせ（crosscheck、`scripts/va.py` と `prompts/tasks/check-list-gap.md`）

review の後、triage の前に動く。決定的な部分はスクリプトが行い、軽量モデルには**一覧 1 つの判定だけ**を渡す。

1. **定義の集合**: テスト以外のファイルから、権限らしい文字列リテラル `"<resource>:<action>"` をすべて集める
   （URL・ハッシュ・MIME などの接頭辞は除く。形式が違う対象は `va.toml` の `perm_pattern` に 1 グループの正規表現を書く）。
   `NAME = "x:y"` の形（Go の型付き定数、TS の `export const`、`NAME := Perm("x:y")` 等）から識別子 → 権限の対応も作る
2. **一覧の候補**: 近い行（間 2 行まで）に、定義済みの権限（リテラルか識別子）またはリソース名が 3 つ以上並ぶ塊。
   `NAME = "x:y"` の行だけの塊は定義そのものなので除く
3. **漏れ**: 定義の集合のうち、その塊に無いもの。無ければ候補にしない
4. **判定（LLM、1 塊 1 呼び出し）**: 一覧が何を分けているか、アクセスの判断に使われるか（`decides_access`）、
   一覧に無いものが緩い側に倒れるか（`fail_open`）、漏れのうちこの一覧に入るべきもの（`missing`、渡した中からだけ選ばせる）。
   一覧の名前の使われ方（最大 8 か所）もプロンプトに入れる
5. **候補化**: `decides_access` が真で `missing` が空でなければ `authz-list-gap` の候補にする（場所は一覧の先頭行）。
   重大度は `fail_open` で上限を付ける（yes: 上限なし、unknown: medium、no: low）。その後は通常どおり別の呼び出しで triage する

コストを抑えるため、同じ塊・同じ漏れの判定は前回の結果を再利用する。1 run の上限は `crosscheck_budget`（既定 30。
ロール・権限らしいパスと `auth` タグのファイルを優先）。上限を超えた分は report の Not covered に出る。

### 限界

- 権限の文字列が実行時に組み立てられる（`resource + ":" + action`）、または DB・外部設定にしかない場合は定義の集合に入らない
- 一覧が別の形（ビットフラグ、正規表現、接頭辞の比較）だと塊として見つからない。接頭辞の比較は `"roles:"` のようなリテラルならリソース名として拾う
- 一覧が別のファイルの識別子を経由する多段の参照は、塊としては見えても使われ方が見えないことがある（そのときは `fail_open: unknown`）

## 3. 再現の確かめ（人が行う。VA は対象を実行しない）

`authz-list-gap` と `privilege-escalation` の finding には、report.md に手での再現手順の雛形が付く。
対象の所有者が、自分で管理する環境（ローカルや検証環境）で次を行う。本番や他人の環境では行わない。

1. テスト用の主体に、ロールを管理する権限だけを与える
2. 漏れていた権限が要る API を呼ぶ → **403** を確かめる（付与の前）
3. その権限を入れたロールを作り、同じ主体に付与する。ここで拒否されれば昇格は起きない（finding は誤り）
4. 2 と同じ API を呼ぶ → **200** なら昇格の再現（付与の後）
5. 対象のコミット、2 と 4 の状態コード、使った権限を記録する

再現できたものは未修正のうちは非公開の脆弱性として扱い、公開の場（Issue・PR・上流への提案）に具体的な権限名や経路を書かない。
上流に返すのは、この文書のような一般化した手法だけにする。

## 修正の方向（fix に書く内容の目安）

- 特権かどうかは allowlist（一般の利用者に渡せる権限の一覧）で判定し、一覧に無いものは拒否する
- 分類を定義の側に持たせる（権限の定義に「特権」「内部用」などの属性を付け、一覧を手書きしない）
- 定義の全件が分類で判定されることを調べるテストを置く（新しい権限を足したときに落ちる）
- 付与の確かめは「付与する権限 ⊆ 呼び出し主体の権限」を、すべての付与の経路で 1 つの関数を通して行う
