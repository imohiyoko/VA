# 上流（VA）への提案ポリシー

VA は **public** です。PR に入ったものは誰でも読め、履歴から消すのは困難です。

## PR にしてよいもの
- `.agents/`, `.claude/`, `templates/`, `scripts/`, `docs/`, `AGENTS.md`, `CLAUDE.md`, `.github/` への変更
- `status: ready` の upstream-candidates から作った変更のみ

## PR に入れてはいけないもの（サニタイズ）
- 対象リポジトリ名・組織名・ドメイン・ホスト名・IP
- 対象のファイルパス、関数名・クラス名など対象を特定できる識別子
- 対象のコード片（一般的なパターンを説明する短い例は、自分で書き直したものなら可）
- シークレット、個人情報、顧客名、社内の製品名・プロジェクト名
- `operator/` 以下のファイルそのもの

例の書き方: 「`/api/admin/users` の認可漏れ」ではなく「管理系ルートでミドルウェアの適用順により認可が外れるパターン」。

## 機械的チェック
提案エージェントは PR 作成前に `scripts/va-sanitize-check.sh` を実行する。
運用リポジトリの `operator/sanitize-denylist.txt`（**運用側だけにある非公開ファイル**）に
対象名・社内用語を1行1つで書いておくと、それらを含む差分・コミットメッセージ・PR のタイトルと本文を拒否する
（denylist を指定して読めないときは失敗する）。
VA 側の CI（`va-guard`）も `operator/` やシークレットらしき文字列を含む PR を拒否する。

## 仕事・他組織の運用リポジトリから提案するとき
雇用先の情報を含む知見を個人の public リポジトリへ出すことになります。
所属組織の情報持ち出しルールを確認し、迷うものは出さないでください。

## PR の形
- 1 PR = 1 テーマ（関連する候補はまとめてよい）
- `.agents/VERSION` を上げ、`.agents/CHANGELOG.md` に1行追記
- PR 本文に根拠（観測回数・対象数・結果の数値）を書く。対象名は書かない
